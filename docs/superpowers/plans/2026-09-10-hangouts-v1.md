# Hangouts V1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a production-safe first StrangerTalks Hangouts slice: temporary anonymous group rooms with real-time text chat, synchronized curated content, collective skip/reactions, reporting, reconnect snapshots, instrumentation and a mobile-first frontend entry.

**Architecture:** Hangouts is a separate bounded context beside the existing pair-shaped Match/Conversation lifecycle. It reuses authenticated participant authority, Repo, Phoenix PubSub and application supervision primitives, but owns its room/membership/message/content/safety persistence and a dedicated `hangout:*` channel. RoomServer is the authoritative source for ordered room state; clients reconcile from snapshots. Channel presence is server/process-owned through a duplicate Registry coupled to the Phoenix transport lifecycle.

**Tech Stack:** Elixir 1.18 CI / Phoenix 1.8 / Ecto/PostgreSQL / Phoenix Channels / plain modular browser JS + CSS / Node 22 test runner.

**Spec:** `docs/hangouts-v1-design.md`

## Global Constraints

- Never mutate pair-shaped `matches` or `conversations` to carry groups.
- Never turn conversation-private media stores into a Hangouts content catalogue.
- No permanent profile, follower, creator or public room identity.
- Language metadata remains extensible text; no eternal three-language enum.
- No anonymous upload-to-public-feed path.
- Server owns message/content sequence, reconnect state and channel-presence authority.
- Clients do not author presence heartbeats or lease identifiers.
- `mix precommit` is mandatory before admission.
- Do not weaken existing tests or workflows.
